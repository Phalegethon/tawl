# TAWL terminal design rules

The closure comparison dedicates four horizontal bands to system resources: CPU, memory pressure, swap amount and swap writes. All four appear in the initial 80×24 view. The request boundary is one third of the way along a fixed −30…+60 second axis. Future time is blank, missing data is dotted, and measured zero follows the baseline. CPU and writes use time-weighted averages with visible coverage; pressure is categorical and swap amount uses each period's final value. Swap amount uses a shared, explicitly zoomed scale. Process outcome and observed system changes remain separate; the interface makes no guaranteed savings or causal claim. PID and request time stay visible even with a long application name. Esc hides the comparison; e returns to the same report. Measurements stop changing after 60 seconds, and only the latest accepted report remains in session memory.

This is an operational terminal interface. Information order is mode/time, pressure, recent resource history, workload comparison and evidence for the selected workload. Thin resource sections and charts replace a plain text-table appearance. There is no decorative animation.

CPU is cyan; GPU purple; memory amber; disk blue; network green. Normal/warning/critical states have both text and green/amber/red indicators. Selection uses a full-row dark cyan background plus a separate marker. Secondary information is readable gray; borders have lower contrast. The terminal's own monospaced font is used. NO_COLOR preserves every meaning through text and shapes.

Numbers align right, and units remain explicit in headings or values. The name column does not grow without limit on wide screens. At ≥120 columns, additional space goes to the selected workload's details. Minimum size is 80×24, with at least six comparable workloads at the minimum and ten at 100×30. History, empty, missing-data and detail states are part of the layout.

Enter opens a one-row-per-process comparison list. Identity and project evidence move to the selected-process panel rather than repeating beneath every row. The panel sits on the right on wide screens and below the list on narrow screens. A second Enter opens the graphical assessment; Esc returns one level. The first assessment view shows a short next step, CPU/footprint history and measured observation durations; longer evidence explanations follow below. Wide assessments put system swap context in a separate area. Old measurements for a disappeared process are explicitly labelled.

Tab cycles through three independent views: application, project and usage category. Categories come from known names; helpers of a recognized application stay in its category, and uncertain matches remain in Other. Application category is not interpreted as the user's current task.

In workload lists, 1–5 select name, CPU, footprint, signed memory change and member count. Process lists use 1–4. Pressing the active key again or r reverses direction. The heading shows field and direction. 0 restores automatic sorting: footprint under memory pressure, CPU otherwise. Manual selection persists; unknown values stay last in both directions. o shows only processes with recommendations. If a selected process stops qualifying, selection moves to a visible candidate or clears if none remain.

High consumption is distinct from resource color: the corresponding numeric cell becomes yellow/red, and CPU!, RAM! or Δ! appears beside the name. CPU ≥1 core is yellow and ≥2 red; footprint ≥2 GiB is yellow and ≥4 red; growth ≥100 MiB in the latest interval is yellow. RAM refers to footprint. These thresholds invite investigation and do not diagnose bottlenecks or leaks.

Charts use actual samples. Freeze and history bind every chart to the displayed sample. System CPU uses 0–100%. Rates show their units on the shared displayed axis; aggregate footprint never becomes a RAM percentage. Inline memory bars are relative to the largest workload in the list.

Process CPU and footprint charts have separate, visible scales. Observation bars represent measured time toward 30/600-second conditions, not confidence scores. Unknown resources or durations use “No evidence”, “?” or a missing-measurement explanation; zero duration means a new or interrupted observation. Missing data never implies healthy or low consumption.

b activates memory focus: it clears search, sorts the main application list by footprint and separates swap amount from both transfer directions. Swap amount, RAM→disk and disk→RAM have distinct labels and scales; reads do not imply an equal decrease in swap amount. Large footprint is neither a proven swap cause nor an estimate of reclaimable GiB; no clearance time is calculated. The action goal is to reduce pressure and new swap writes, then compare the result. Accumulated swap alone does not justify a closure recommendation. See the [swap research note](docs/research/2026-10-22-swap-evidence.md).

Recommendations explain observation, reason and action separately. Sustained CPU requires ≥1 core for 30 seconds; a memory recommendation requires system pressure and ≥2 GiB footprint. A low-activity candidate requires age ≥2 hours and 600 uninterrupted seconds of known CPU <0.02 cores, disk reads and writes each <1 KiB/s, and footprint ≥256 MiB. Per-process network and user interaction are unknown, so the interface never concludes “unused”.

Age and ownership eligibility come from local measurements and remain unknown when absent in old recordings. Unverified ownership and system/database/VM services receive no closure recommendation. Saving work and normal application exit come first. For a live application process, x opens the control dialog and Enter opens confirmation with the affected application and single-PID scope. Cancel is selected initially. SIGTERM is not an application Quit action and does not guarantee a save dialog. Historical recommendations retain the requirement for live validation.

Duration evidence is independent of full chart history and bounded to current process identities and 30/600-second counters. Identity loss, missing measurements and time gaps interrupt the duration. Freezing a live view preserves its evidence; later samples cannot change historical recommendations. Moving to another historical sample never carries future evidence backward.

Full-screen behavior uses the alternate screen buffer. Rendering uses absolute cursor positioning (CUP), emits no LF, and disables automatic line wrapping. SGR/X10 vertical wheel reports navigate the list or assessment. Terminal modes are restored on exit. Shell history is preserved; scrollbar visibility and forwarding wheel input depend on the terminal host. Persistent terminal preferences are never changed.

Closure confirmation stays bound to one process lifetime while lists update. The affected application, PID, reason and data-loss implications appear together. Long impact text must be viewed to its end before approval can execute. Enter first collects a fresh measurement; changed ownership, application or process identity rejects the request. A changed recommendation does not override explicit user selection. Only SIGTERM is sent, using a single-use native audit token valid for 30 seconds. Pending, confirmed exit, still running, identity changed and unknown outcome are separate states. Signal acceptance alone is not closure success. Pasted content is not executed as commands when the terminal supports bracketed paste.

x always opens a visible closure-control dialog; eligibility checks never hide it. Tab changes between selected-workload and all-recommendations scopes. Selection performs no native preparation. Enter opens a separate confirmation with an immutable target. Rejection and permission errors remain in the control area. Frozen/history views provide an explicit return to live data. SUGGESTED and MANUAL are distinct: a verified owned application process can be selected without an automatic recommendation. System/database/VM and identity protections remain in place.

In the comparison, d produces one HTML file. The result dialog shows the complete path, a opens it in a browser, and d retries a failed save. HTML uses a light background, identity/outcome information, an aligned before/after table, four SVG charts sharing a time axis, and interpretation limits. On narrow browsers, tables and charts scroll within their containers rather than overflowing the page; charts do not split when printed. Partial/completed, missing/zero/future and process outcome/system change remain distinct.

The hardware area is visible at launch; g switches to the original summary charts. CPU cores share a 0–100% scale. E/P labels require direct topology evidence. GPU is purple and represents the whole device; core count is separate metadata. ≥80% yellow and ≥95% red highlight current load. Narrow terminals use single-line CPU charts; wide terminals use a grid. At least six application rows remain at 80×24. [ / ] reach every core/device page; each GPU has one chart. Hardware uses the same source as the frozen or historical selection.

English is the default language. `--lang en|tr` overrides `TAWL_LANG`; absent either, English is used regardless of OS locale. Localized copy must preserve metric meaning, units, alignment, keyboard controls and missing-data semantics. Turkish translations belong in the translation catalog; project documentation and source-facing explanations use English.
